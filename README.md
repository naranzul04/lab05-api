## 1. Сонголт ба төлөөлөх утгын хүснэгт (`POST /registrations`)

Лекц 5-ын тест дизайны дагуу `POST /registrations` функцийн оролтын хүчин зүйлсийг сонголт ба төлөөлөх утгуудад (эквивалент ангиудад) хуваав:

| № | Сонголт (Choice) | Төлөөлөх утгууд / Эквивалент ангиуд | Тайлбар |
| :- | :--- | :--- | :--- |
| 1 | `studentID` хүчинтэй ба төлөв | • Идэвхтэй (`"active"`)<br>• Идэвхгүй (`"inactive"`)<br>• Байхгүй (`PUT` хийгдээгүй)<br>• Дутуу / хоосон (`""`, `null`, талбар орхигдсон) | Оюутны бүртгэл болон идэвхтэй төлөвийг шалгана |
| 2 | Оюутны үзсэн хичээлүүд (`coursesTaken`) | • Урьдач нөхцөлийг бүрэн хангана<br>• Урьдач нөхцөлийг хэсэгчлэн хангана<br>• Урьдач нөхцөлийг огт хангахгүй (`[]` эсвэл өөр хичээл) | `PUT /students/:id` хүсэлтээр тохируулна |
| 3 | `courseID` хүчинтэй байдал | • Байгаа (`PUT` хийгдсэн)<br>• Байхгүй (серверт бүртгэлгүй)<br>• Дутуу / хоосон (`""`, `null`, талбар орхигдсон) | Хичээлийн бүртгэлийг шалгана |
| 4 | Хичээлийн урьдач нөхцөл (`prerequisites`) | • Хоосон / байхгүй (`[]` эсвэл орхигдсон)<br>• Нэг урьдач нөхцөлтэй<br>• Олон урьдач нөхцөлтэй | `PUT /courses/:id` хүсэлтээр тохируулна |
| 5 | Хүсэлтийн биеийн JSON бүтэц | • Зөв JSON формат<br>• Буруу / эвдэрсэн JSON синтакс | `400 ERROR_BAD_JSON` нөхцөлийг шалгахад |

## 2. Тестийн спецификацийн хүснэгт

Нийт **11 тест кейс** (10 үндсэн API тест + 1 нийтийн API тест) болон **23 assertion** тодорхойлов. Тест бүр өөрийн `PUT` setup хүсэлтийг ажиллуулдаг тул бие даасан бөгөөд `registrationID`-ийн яг утга (`== 1`) бус, тоон төрөлтэй эсэхийг шалгасан.

| ID | Ангилал | Сценари / Нөхцөл | Хүлээгдэх HTTP статус | Хүлээгдэх `result` / Үр дүн |
| :- | :--- | :--- | :---: | :--- |
| **TC-01** | Happy Path | Идэвхтэй оюутан (`S1001`) урьдач нөхцөлөө (`CS102`) хангасан үед `SE305`-д бүртгүүлэх | **201** | `"OK"` ба тоон `registrationID` |
| **TC-02** | Алдааны анги 1 | Бүртгэлгүй оюутан (`S9999`) бүртгүүлэх гэж оролдох | **200** | `"ERROR_NO_STUDENT"` |
| **TC-03** | Алдааны анги 2 | Идэвхгүй оюутан (`S1002`, `status: "inactive"`) бүртгүүлэх | **200** | `"ERROR_INACTIVE_STUDENT"` |
| **TC-04** | Алдааны анги 3 | Байхгүй хичээл (`XX999`) руу бүртгүүлэх | **200** | `"ERROR_NO_COURSE"` |
| **TC-05** | Алдааны анги 4 | Урьдач нөхцөл дутуу (`S1003` нь `CS102` үзсэн, `SE410`-д `CS102, CS210` шаардана) | **200** | `"ERROR_PREREQUISITES"`, `missing: ["CS210"]` |
| **TC-06** | Давхар алдаа 1 | Идэвхгүй оюутан (`S1002`) + байхгүй хичээл (`NO_COURSE`) | **200** | `"ERROR_INACTIVE_STUDENT"` (оюутны төлөв түрүүлж шалгагдана) |
| **TC-07** | Давхар алдаа 2 | Байхгүй оюутан (`NO_STUDENT`) + байхгүй хичээл (`NO_COURSE`) | **200** | `"ERROR_NO_STUDENT"` (оюутан байгаа эсэх түрүүлж шалгагдана) |
| **TC-08** | Хязгаар (Boundary) | Урьдач нөхцөлгүй хичээлд (`CS101`, `[]`) хоосон `coursesTaken` (`[]`) оюутан (`S1004`) бүртгүүлэх | **201** | `"OK"` |
| **TC-09** | Хязгаар (400) | Шаардлагатай `courseID` талбар дутуу хүсэлт илгээх | **400** | `"ERROR_BAD_REQUEST"` |
| **TC-10** | Хязгаар (400) | Буруу / эвдэрсэн JSON форматтай хүсэлт илгээх | **400** | `"ERROR_BAD_JSON"` |
| **TC-11** | Нийтийн API (Даалгавар 5) | `GET https://jsonplaceholder.typicode.com/users` хүсэлт илгээх | **200** | Хоосон биш массив, `users[0].name === "Leanne Graham"` |

## 3. Newman тест ажиллуулалтын үр дүн

| Горим | Гаралтын файл | Assertions executed | Assertions failed | Exit code | Тайлбар |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **PASS** | `results/newman-pass.txt` | **23** | **0** | **0** | Бүх тест амжилттай давсан (`iterations: 1`, `requests: 22`, `test-scripts: 11`) |
| **FAIL** | `results/newman-fail.txt` | 23 | ≥ 1 | **1** | Зориуд өөрчилсөн oracle унаж, exit code `1` буцаасан (CI quality gate) |
| **DOWN** | `results/newman-down.txt` | 0 | 0 | **1** | Сервер унтарсан үед `ECONNREFUSED` холболтын алдаа гарсан |

* **Интерфейсийн алдаа vs Oracle-ийн алдаа:** `ECONNREFUSED` нь сервер унтарсан эсвэл холболт үүсээгүйгээс үүдэлтэй **интерфейсийн (холболтын) алдаа** бөгөөд HTTP хариу ирээгүйгээрээ серверээс ирсэн хариу хүлээгдэж буй шаардлагатай зөрөх үед үүсдэг **oracle-ийн алдаа**-наас ялгаатай.
* **Локал API ба Нийтийн API харьцуулалт:** Локал `POST /registrations` API дээр тест бүрийг бие даасан байлгахын тулд `PUT` setup хүсэлтүүд болон төлөвийн хослолуудыг бэлтгэх шаардлагатай байсан бол `GET https://jsonplaceholder.typicode.com/users` нь төлөв өөрчилдөггүй тул setup-гүйгээр шууд шалгахад хялбар байв.

* `iterations`: executed `1`, failed `0`
* `requests`: executed `22`, failed `0`
* `test-scripts`: executed `11`, failed `0`
* `assertions`: executed `23`, failed `0`
* Бүтэн гаралтууд `results/newman-pass.txt`, `results/newman-fail.txt`, `results/newman-down.txt` файлуудад хадгалагдсан.

## 4. Дүгнэлт

Тест дизайны 5 алхмаас сонголтуудыг ялгаж, эквивалент ангиудад хуваах болон давхар алдааны тохиолдлуудыг бодох нь хамгийн их толгой ажиллуулсан хэсэг байлаа. Оюутны төлөв, бүртгэл, хичээл, урьдач нөхцөл, JSON формат гээд олон хослол гарах ч байхгүй оюутан дээр үзсэн хичээл ярих, байхгүй хичээл дээр урьдач нөхцөл ярих зэрэг утгагүй хослолууд таарсан тул тэдгээрийг ялгаж хассан. Мөн нэг хүсэлтэд хэд хэдэн алдаа зэрэг байхад аль нь түрүүлж буцахыг зааварт хэлээгүй байсан болохоор өөрөө туршиж үзээд, сервер эхлээд оюутан байгаа эсэх болон идэвхтэй эсэхийг шалгадаг болохыг мэдэж авлаа. Тест бүр дээр өөрийн `PUT` setup хийсэн нь өмнөх хүсэлтээс болж өгөгдөл холилдох эсвэл `registrationID` дараалан өсөхөөс сэргийлэхэд их хэрэг болсон. Нийт 23 assertion бүгд амжилттай давсан бөгөөд `server.js` дээр шинэ программ кодын согог илрээгүй ч давхар алдааны дараалал болон тестүүдийн бие даасан байдлыг шалгасан нь чухал байв. Мөн `FAIL` болон `DOWN` горимд exit code `1` гарсан нь ямар нэг алдаа эсвэл холболтын асуудал гарахад автомат шалгалт шууд зогсдог зарчмыг бодитоор харууллаа. Ингээд гараар тест бичихээс эхлээд Newman-аар автоматжуулах хүртэлх бүх үе шатыг хийж үзэхэд API тестийн логик илүү ойлгомжтой боллоо.

## 5. Нэмэлт даалгавар: AI-тай харьцуулсан миний дүгнэлт

`POST /registrations` дээр Лекц 5-ын дагуу сонголт, эквивалент анги, тестүүдийг AI-аар гаргуулаад өөрийнхтэйгөө харьцуулж үзлээ. AI үндсэн кейсүүд болох амжилттай бүртгэл (`201 OK`), байхгүй эсвэл идэвхгүй оюутан, байхгүй хичээл, урьдач нөхцөл дутуу зэргийг зөв гаргасан ч давхар алдааны эрэмбийн зарим тохиолдол болон `coursesTaken` хоосон үеийн нарийн хувилбаруудыг гүйцэд гаргаагүй байв. Харин миний талд талбар дутуу (`400 ERROR_BAD_REQUEST`), буруу JSON (`400 ERROR_BAD_JSON`) болон давхар алдаанд аль нь түрүүлж буцахыг илүү тодорхой ялгаж чадсан нь давуу талтай байлаа. Нөгөөтэйгүүр, AI-ийн гаргасан санаануудаас `PUT` хийхэд `status` болон `coursesTaken` автоматаар анхдагч утга авдгийг дахин нягталж, өөрийн setup өгөгдлүүдээ илүү цэгцтэй шалгахад нэмэр болсон. AI-ийн бичсэн oracle-ууд энгийн нөхцөлүүдэд ихэнхдээ зөв байсан ч давхар алдаа эсвэл `missing` массив дээр заримдаа хэт ерөнхий таамаг маягаар бичигдсэн байв. Тест бүр дээр өөрийн `PUT` setup хийх нь өмнөх хүсэлтээс болж `registrations` өсөх зэрэг нөлөөнөөс сэргийлэхэд их хэрэг болсон. Ер нь AI-аар санаа болон анхны загвар хурдан гаргуулж болох ч эцсийн тест, oracle хоёрыг заавал кодтойгоо тулгаж, өөрөө ажиллуулж шалгах нь хамгийн зөв юм байна.
